# Review-режим: отклики с ревью в Telegram

Команда `apply-review` (подкласс `apply-vacancies` из hh-applicant-tool). Обход по резюме по расписанию cron:

| Вакансия | Что происходит |
|---|---|
| детектор нашёл промпт-инъекцию | в Telegram: полный текст вакансии, вердикт с цитатами → ревью письма (+ анкеты) |
| `response_letter_required` | ревью письма (+ анкеты) |
| есть анкета | ревью анкеты |
| иначе | отклик резюме без письма, автоматически |

Уже откликнутые, архивные и вакансии с откликом на сайте работодателя пропускаются.
Отсев (`--excluded-filter`, `--ai-filter`, `--skip-tests`, `-f`) в этом режиме не применяется.

## Ревью в Telegram

Ревью — сплошной поток, а не очередь: обход доходит до вакансии, которой нужно письмо или анкета, и **встаёт**. Карточка сразу приходит в чат (в чате «⏸ Обход стоит — жду твоего решения» с таймером). Апрув или реджект — обход берёт следующую вакансию. Очереди карточек нет, копиться нечему. Если обход оборвали (перезапуск, капча) на открытой карточке, следующий обход сперва дорешивает её. После апрува обход ждёт отправки отклика ботом (до 30 с).

- **Черновик письма** приходит двумя сообщениями: короткая шапка с подсказкой и **голый текст письма** отдельно — «Копировать» на нём даёт ровно то, что уйдёт в hh. Служебные строки бота (метка резюме, «✉️ Письмо (черновик)», подсказка про кнопки) в письмо не пускаются: чистятся при приёме правки и ещё раз перед отправкой (`letters.py`, событие `letter_cleaned`).
- **Письмо:** ✅ апрув — уходит черновик · ✏️ эдит — пришли свой текст, уйдёт он · ❌ реджект — вакансия пропускается.
- **Анкета:** любой текст — промпт для LLM (правит и показывает изменения ✏️); `N: текст` — ответ N заменяется дословно (для выбора — номер варианта, `2: 1,3` для нескольких); ✅ апрув и ❌ реджект в любой момент.
- Команды: `/current` — повторить карточку, `/queue` — что открыто и что ждёт отправки.

После апрува всех шагов вакансия отправляется в hh (`review-submit`). Вне окна работы — ждёт окна.

## Два бота

- **Основной** (`review.telegram`) — вся работа: карточки ревью, капча, лента откликов, отсчёты пауз с кнопкой ⏭, спиннер проверки.
- **Уведомлений** (`review.notify`) — только «нужно участие»; ничего не принимает. По одному сообщению со звуком и кнопкой «▶️ Открыть бота»:
  - 📝 **Нужно ревью** — пока карточка не решена (обход при этом стоит); забытое напоминает новым сообщением раз в 20 минут; решённое становится итогом («✅ Ревью решено: апрув»);
  - 🧩 **hh просит капчу** — пока не решена;
  - ⏳ **пауза до следующего обхода** — самая долгая из пауз; тихо, исчезает вместе с паузой;
  - ошибки процессов (traceback) идут туда же.
  Решённые строки живут сутки, потом бот убирает их из чата. Состояние хранится в БД: перезапуск ничего не дублирует.

Смена токена основного бота безопасна: при первом старте с новым ботом бот сбрасывает смещение getUpdates, id сообщений с кнопками/отсчётами/картинками капчи и присылает открытую карточку целиком; из чата старого бота сообщения убираются, если его токен теперь `review.notify`. Меню команд перекрывается нашим во всех областях личного чата.

## Модель (opencode_ssh: OpenCode на удалённом хосте)

- Инструменты у модели отключены: каждый запрос разрешения на инструмент (`webfetch` по ссылке на тестовое, `bash` и т. д.) сразу отклоняется, попытка записывается в `tool_attempts` (признак инъекции для детектора).
- Отклонять нужно **по потоку событий `/event`**, а не по списку `GET /permission`: у запроса `webfetch` в metadata поле `timeout` пустое, сервер OpenCode (1.18.31) не может его сериализовать и отвечает 400 на каждый `GET /permission`, пока запрос висит (так может встать вся модель). Драйвер переживает сломанный список (`llm_permission_list_broken` в журнале); инструмент, зависший без ответа дольше 25 с, даёт быстрый отказ `tool_blocked` и один повтор с напоминанием «инструментов нет».
- Если модель не отвечает 3 оценки подряд, обход останавливается (`llm_dead`, один алерт); следующий обход по cron пробует снова. Карточка без черновика показывает «🔁 Повторить» / «❌ Реджект».

## Капча

Ключ капчи у hh живёт около минуты. Поэтому бот присылает не картинку, а сообщение «🧩 Показать капчу»; картинка создаётся по кнопке и висит с обратным отсчётом (55 с). Протухла — картинка убирается, снова кнопка. Ответ на протухшую картинку в hh не отправляется (он сгорел бы как «неверный»): бот сразу присылает свежую. Так первый ответ не «всегда неверный», как было, когда картинка ждала человека минутами.

## Настройка — `config/config.json`

```json
{
  "review": {
    "telegram": {"bot_token": "…", "chat_id": 123, "proxy_url": null},
    "notify": {"bot_token": "…", "chat_id": 123},
    "work_hours": null,
    "max_queue": null,
    "injection_llm": true,
    "style_file": "style.md"
  },
  "llm": {"driver": "opencode_ssh", "host": "<ssh-хост>", "user": "<ssh-пользователь>", "key_file": "~/.ssh/<ключ>", "model": "<provider>/<model>"}
}
```

- `work_hours` — окно `HH:MM-HH:MM` (по `TZ` контейнера), `null` — круглосуточно. То же параметром `--work-hours`.
- `max_queue` / `--max-queue N`, `--max-responses N` — лимиты, по умолчанию без ограничения.
- `injection_llm` — проверять инъекции ещё и моделью (кроме эвристик). Модель недоступна → обход ждёт её до `llm_wait` секунд (по умолчанию 600, `--llm-wait`); не ожила — вакансия идёт на ревью, авто-отклика мимо проверки нет.
- `apply_delay` / `--apply-delay 60-180` — случайная пауза между реальными откликами (секунды, `0` — без паузы).
- `max_per_hour` / `--max-per-hour 10` — не больше N реальных откликов за скользящий час (`0` — без лимита); сверх — в следующем обходе.
- Поток ревью без очереди включён всегда (кроме dry-run): в него попадают письмо, анкета, подозрительная вакансия и описание, которое просит что-то в письме. `--no-block-on-review` — только для отладки, возвращает очередь карточек.
- `notify` — необязателен; `chat_id` по умолчанию тот же, что у основного. Без него пингов нет, ошибки идут в основной чат.
- Отправка из бота (`review-submit`) живёт по тем же числам, что обход: `limits.max_per_hour` и `timeouts_sec.apply_delay` из `conf.json`. Пока обход ждёт человека, застрявшее на лимите письмо уходит, как только окно часа освободилось.
- Капча hh: обход останавливается, основной бот присылает кнопку «Показать капчу» (см. выше); после успеха бот сам запускает новый обход по `conf.json`.
- Ошибки любой команды приходят с traceback в бот уведомлений; лог процессов: `config/log.txt`, вывод cron: `docker compose logs cron`.
- `relevance_profile` (необязательно) — предпочтения по роли и формату работы свободным текстом (до 1500 символов); добавляется в промпт оценки релевантности. Пример: «Ищу роль дата-аналитика. Роли без работы с данными оценивай низко. Гибридный формат допустим.».
- `config/style.md` целиком уходит в промпт писем и анкет вместе с резюме.

## Команды

```sh
stamp-flow apply-review [--dry-run] [--work-hours 09:00-21:00] [--max-responses N] [--max-queue N]
stamp-flow review-bot          # демон Telegram-бота
stamp-flow review-submit <id>  # отправить одобренную вакансию (вызывает бот)
stamp-flow review-demo [--llm] # демо-вакансии в очередь (dry-run, в hh ничего не уходит)
stamp-flow llm "вопрос"        # проверить LLM-драйвер
```

## Docker

```sh
docker compose build
docker compose run --rm -u app cron python -m stamp_flow -vv auth -k   # вход в hh
docker compose run --rm -u app cron python -m stamp_flow apply-review --dry-run --max-responses 3
python run.py   # по conf.json: пишет config/crontab и поднимает cron + bot (docker compose up -d)
```

SSH-ключ берётся из каталога `HH_SSH_DIR` (лучше отдельный, только с нужным ключом) и копируется в контейнер с правами 600.

## Журнал (не удаляется)

- SQLite (`config/data`): `review_items` — состояние, `review_events` — все события: вакансии, вердикты, запросы и ответы LLM, решения, правки, ответы hh. UPDATE/DELETE журнала и DELETE вакансий ревью запрещены триггерами.
- Копия: `config/review-log/YYYY-MM.jsonl`, только дозапись.
- Посмотреть: `stamp-flow query "SELECT ts, type, vacancy_id FROM review_events ORDER BY id DESC LIMIT 20"`.
